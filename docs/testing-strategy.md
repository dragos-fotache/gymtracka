# Android testing strategy

Procedures and coverage boundaries, not a chronological test journal. Actual per-task execution belongs in its acceptance
review; [recorded verification](#recorded-verification) below is a compact evidence index, not a fresh pass.

## Layers and conventions

| Layer | Use for | Boundary |
|---|---|---|
| Offline JVM | Models/codecs, formatting, state holders, transport and session fault/race tests | No external backend configuration; local TLS/scripted I/O is allowed |
| Real Room instrumentation | Transactions, rollback, queries, cascades, scoped capture, migrations | Real in-memory databases; do not mock DAOs |
| Compose/app-flow instrumentation | Controls, autosave, navigation, persisted journeys and timer coordination | Stable semantics; exercise actual app construction as well as isolated controls |
| Isolated real-backend JVM | Production sync/auth wire interoperability and real service outcomes | Separate explicit task; not Google OAuth or Room engine convergence |
| Python launcher/catalogue | Isolated-resource safeguards and fixed-seed parity | Separate from JVM/device evidence |
| Live journeys | Real Google, installed signing, phone/laptop HTTPS, background and lifecycle behavior | Explicit owner-approved inputs; cannot be closed by mocks |

- Test behavior/invariants rather than private implementation details or incidental Compose layout.
- Use hand-written narrow repository/transport/hardware doubles, `TestScope`, virtual time and deterministic gates; no
  sleeps or backend-sized simulator. Real service tests do not replace deterministic client failure/cancellation tests.
- Inject repository, scope, clocks, UUIDs, and hardware only where needed, keeping production constructor paths usable.
- Independent expectations must not be generated by the production encoder under test. Contributor source separation
  and serialized Gradle slots follow [coordinator workflow](coordinator-workflow.md).
- Every entity change needs KSP/schema export, a data-preserving migration, all supported starting versions, and a copied
  real v1 asset. Preserve schema snapshots; never use destructive fallback.

## Proportional coverage and verification gates

Choose coverage by **risk and distinct plausible defects**, not test-count, coverage-percentage or test-line quotas.
Keep existing tests; this policy narrows future additions and routine execution, not established safety requirements.
Exhaustive matrices and full-stack verification are not the default for every bounded slice.

### Test scope

| Change | Proportionate new coverage |
|---|---|
| Small formatting or presentation change | Focused JVM/component tests for changed behavior; no automatic full device run. Use a focused Compose test when the changed interaction requires it |
| Feature behavior | Changed success paths, important failure paths and relevant existing regressions |
| Persistence, sync or authentication | Explicit affected safety-invariant matrix, real Room where transactions matter, and representative cancellation/restart/race cases |
| Schema change or cross-feature activation | Full relevant regression, every-supported-start plus bundled-asset migration coverage, and appropriate integration gates |

- Each new test must identify a distinct plausible defect and an independently expected observable result. Prefer the
  narrowest layer that can prove it. Do not add tests solely to enumerate trivial result shapes, constructors or enums.
- Reuse existing codec/validator and prerequisite coverage rather than repeat its entire matrix in each consumer.
  Add a focused integration check that the changed boundary uses it correctly. Repeat a case at another layer only
  when that layer introduces a distinct failure risk, such as Android parser behavior or transaction rollback.
- Use representative failure classes when they share a recovery path; do not multiply every account/type/field/timing
  combination unless it exercises a distinct implementation path or consequence. Table-driven cases can reduce
  boilerplate but are not a substitute for independent expectations.
- Retain rigorous tests for affected edit durability, atomic rollback, exact uncertain-write retries, newer-intent
  preservation, account/privacy fencing, credentials and destructive actions. Scope reduction never waives these
  invariants, data-preserving migrations or finalized shared-contract/milestone requirements.
- Reuse vetted deterministic test fixtures, gates and snapshot helpers instead of building another bespoke harness
  for each slice. Respect contributor access boundaries; the coordinator supplies concrete API/harness facts so QA
  does not have to guess signatures or inspect production. Keep independent QA and final coordinator review.

### Execution cadence

1. **Iteration:** compile the changed source and run affected tests. After a correction, rerun the failing cases and
   impacted regressions, not every layer automatically.
2. **Slice acceptance:** run affected tests plus the inexpensive full offline JVM suite for code changes. Execute focused
   Room/Compose tests when the changed behavior requires them; compiling instrumentation is not a behavior pass.
3. **Package/integration milestones:** run full unfiltered instrumentation, assembly/lint and applicable backend gates.
   Bring these gates forward for cross-cutting or high-risk changes. Packaging, dependency, configuration or security
   changes require their relevant assembly/lint/APK checks at slice acceptance, not only at a later milestone.
4. **Activation/release:** retain all required convergence, migration, device/API, security and authorized live gates.
   Representative unit tests never replace integration or live evidence required for that milestone.

Each bounded specification selects its risk, distinct new-test obligations, reused coverage, iteration checks and
acceptance gates **before delegation**, including when deferred broad gates will run. There is no fixed test-count
budget. A focused slice may be accepted without a fresh full device run when its declared scoped gates pass; record
that boundary and the deferred milestone explicitly, rather than claiming full regression. Unavailable required gates
remain unverified and cannot be silently deferred to claim completion. Documentation-only work needs documentation
validation, not build/test execution.

Measure authoring/review effort, fixture corrections, emulator setup and build/test execution separately when adjusting
future assignments. Total test count alone does not explain delivery time or justify further suite growth.

## Standard commands

Run from the Android repository root. The commands below are a **menu, not a checklist for every slice**; select them
using the [execution cadence](#execution-cadence). A source change requires compilation and relevant tests; code-slice
acceptance also includes the full offline JVM suite. Add Room/Compose execution and broader gates where required
by the declared risk and milestone, not merely because those layers exist.

```sh
./gradlew :app:compileDebugKotlin --console=plain
./gradlew :app:testDebugUnitTest --console=plain
./gradlew :app:compileDebugAndroidTestKotlin --console=plain
./gradlew :app:assembleDebug :app:lintDebug --console=plain
# Requires an available emulator/device; unfiltered full layer.
./gradlew :app:connectedDebugAndroidTest --console=plain
git diff --check
git -C shared-docs diff --check
```

For new execution evidence, ensure the **intended test task** really executes; an up-to-date/cached test task is not
another test pass. Reuse valid cached compilation/build dependencies. Gradle's task-scoped `--rerun` avoids rebuilding
all dependencies merely to execute tests:

```sh
# Typical code-slice JVM acceptance: rerun tests, not every compilation/KSP/build task.
./gradlew :app:compileDebugKotlin :app:testDebugUnitTest --rerun --console=plain
# Focused JVM iteration; replace the illustrative class with the affected class or method.
./gradlew :app:testDebugUnitTest --tests 'com.dragosfotache.gymtracka.data.sync.PushClaimContractTest' --rerun --console=plain
```

Do not use blanket `--rerun-tasks` or disable configuration caching routinely. Reserve from-scratch rebuilds/cache
troubleshooting for a concrete stale-output concern, build/dependency change or explicitly required audit, and record
why. For package/integration/release gates, run unfiltered instrumentation and applicable separately configured backend
checks. Missing device/backend inputs leave required gates unverified. Documentation-only changes require link,
whitespace, diff and scope-preservation checks, not an invented build/test pass.

Inspect actual nested XML `testcase` names/counts/failures/errors/skips; table-driven subcases are not extra test counts.
Keep failed shell exits visible. Verify **executed classes as well as totals** against every requested filter. In the
R09a environment a comma-separated runner `class` argument executed only its first class; package filters and separate
single-class invocations supplied the actual scoped gates. Do not infer all requested classes ran from a green Gradle exit
or use those filtered runs as full unfiltered regression evidence. Relevant reports:

- JVM: `app/build/test-results/testDebugUnitTest/`, `app/build/reports/tests/testDebugUnitTest/`.
- Device: `app/build/outputs/androidTest-results/connected/debug/`, `app/build/reports/androidTests/connected/debug/`.
- Lint: `app/build/reports/lint-results-debug.xml`; APK: `app/build/outputs/apk/debug/app-debug.apk`.
- Backend: `app/build/test-results/testRealBackend/`, `app/build/reports/tests/testRealBackend/`.

Catalogue join-table foreign-key-index KSP warnings and recorded newer-dependency lint findings are nonfatal baseline
findings, not permission to hide new warnings. Record any new warnings and limitations in the relevant review.

## Isolated real-backend procedure

Backend access is build/start plus black-box HTTP only, not source review/changes or its Maven suite. Do not read personal
configuration or use personal databases. In a separately owned foreground terminal:

```sh
python3 scripts/run-isolated-backend.py --backend-root /home/dragos/IdeaProjects/gt-backend
```

The launcher builds the JAR, starts disposable PostgreSQL 16, generates test-only keys and publishes an exclusive mode-600
`/tmp/gymtracka-real-backend/config.json`. Use `--no-build` only for an already-built appropriate JAR. Existing config paths
and occupied ports are refused; choose another `--config-path`/`--port` instead of overwriting or killing unrelated work.
Stop with Ctrl+C; cleanup owns only its process/container/config. Never assume an archived service is still running.

```sh
./gradlew :app:testRealBackend -Pgymtracka.realBackendConfig=/tmp/gymtracka-real-backend/config.json --console=plain
python3 -B -m unittest discover -s scripts/tests -p 'test_*.py'
```

`GYMTRACKA_REAL_BACKEND_CONFIG` is the alternative configuration input. Missing configuration fails, never skips. The
real-backend task excludes the offline task as a dependency and always executes against external state with build caching
disabled. Ordinary JVM tests exclude the backend package and need no service.

`RealBackendFixture` checks configuration ownership/mode, loopback/disposable database identity and run guards before
creating isolated session credentials. Domain mutations/reads go through HTTP, not SQL fixtures. Production sync/auth
adapters use a test-only locally trusted TLS relay; JDK/JDBC/certificate/relay helpers remain outside the APK. Setup bypasses
external Google only for isolated credentials; it neither adds a service auth bypass nor verifies a successful real Google
exchange. Local interoperability is not deployed TLS, phone behavior, or real Room-backed engine convergence.

## Catalogue verification

The shared package owns seed details and tool instructions. Offline Android parity checks:

```sh
python3 shared-docs/catalogue/verify.py --android-db app/src/main/assets/databases/gym.db
python3 -B -m unittest discover -s shared-docs/catalogue -p 'test_*.py'
```

When packaging/seed inputs change, check source-asset parity and byte-identical packaged database/notices. Do not edit the
v1 asset to add user data. Seed tests are not Android JVM/device tests.

## Instrumentation and coroutine lessons

- A successful connected-task shell exit is not test execution proof: native ADB authorization/collector failures can
  produce zero cases despite `BUILD SUCCESSFUL`. Check the selected device and actual nonempty executed XML before
  recording a pass; correct only test-owned emulator authorization, preserving unrelated devices/configuration.
- Use normal emulator ADB registration for the native runner. An isolated-server device can be discovered by DDMLIB
  but not found by native ADB; a TCP alias can also produce nonzero native-task exits despite zero-failure XML. Diagnose
  only owned resources, preserve failures, and require successful fresh tasks plus nonempty XML; direct `am instrument`
  diagnosis never substitutes for a required Gradle gate. Do not restart unrelated ADB servers or use personal devices.
- Filter by one fully qualified class or `Class#method`. Comma-separated filtering selected only the first intended
  class/method in the recorded local environment; inspect executed XML rather than assuming all filters ran.
- A filtered pass is not a full regression. Use unfiltered execution for a full-layer claim.
- Use Compose testing v2 `createComposeRule` scheduling, one `setContent` per test, bounded `waitUntil` on actual UI/Room
  outcomes and `runOnIdle` for callback assertions. Avoid sleeps/busy-yield loops or `waitForIdle` alone after Room writes.
- Do not block the Compose test thread with runBlocking on an app/feature drain whose outcome needs its test scheduler.
  Launch acquisition asynchronously, drive a bounded waitUntil on completion, then await only that completed result.
  Use per-test runner and outer command timeouts for device gates; a hanging run with no completed XML is not a pass.
- Dispose composition and cancel/join owned state scopes before closing Room. Teardown timeouts fail rather than being swallowed. Isolated interaction tests may preload
  state; actual app flows must verify normal factories without preload, using the internal repository override and
  no-op timer hardware. Inspect unmerged semantics/logcat before guessing at loading failures.
- Preservation oracles belong after any deliberately allowed capture/admission and before the operation under test.
  Resetting outbox rows does not remove physical domain UUIDs; reuse existing rows or use distinct fixture identities.
  Exact schema comparison excludes new tables by `sqlite_master.tbl_name`, including their PK autoindices, not just
  named-index whitelists. Retain complete old-table/sequence comparisons and demonstrate the next allocation.
- Coroutine exception identity assertions belong inside the actual caller, not across `async.await` stack recovery.
  Gate actual I/O/cancellation entry and check the intended child context; a test receiver's context can select its parent.
  Capture a canceled child's outcome separately and join it; awaiting a canceled Deferred still throws despite a caught
  cancellation. A queued Mutex cancellation probe may itself be stack-recovery copied: use a test-only non-copying
  `CopyableThrowable` probe for an exact-reference oracle, never disable global debug/stack recovery. Already-canceled
  entry tests must actually enter the child before self-canceling/calling the API; a default-start child canceled before
  scheduling never executes its body.
- Prove pre-suspension input ownership with a transaction-executor admission barrier and a separate query executor.
  Start the handler `UNDISPATCHED` inside an inherited `coroutineScope`, await its captured transaction runnable, then
  mutate inputs before admission. A generic first-query callback can race earlier/background work during capture.
- Query callbacks run before their SQL executes. To cancel after a bookkeeping/canonical write, observe the write and
  cancel on the following query, assert the hook fired, and compare complete persisted state after rollback. Merely
  cancelling on the write callback does not prove post-write cancellation. For canceled-child token checks, launch
  through an explicit inherited `coroutineScope` inside the live run: a `runTest` receiver's `async` can lose the run
  context marker. Keep the parent run active to prove old-token rejection plus unchanged fresh readmission.
- Separate rollback from lost-result-after-commit evidence: a captured transaction executor can signal after its Room
  runnable returns while a test-only queued caller dispatcher holds result resumption. Inspect actual durable state,
  cancel before delivery, then recover using a fresh durable-epoch run. No sleeps or result/token-success inference.
  A lease-close failure after publication similarly does not prove rollback; inspect durable dirty/materialized epochs.

## CI

[The workflow](../.github/workflows/android-tests.yml) has separate build/JVM/assembly and instrumentation jobs. It uses
Ubuntu 24.04/JDK 25 and installs API 37 SDK/build tools; instrumentation uses a headless API 35 Google APIs x86_64 emulator
on pull requests/manual dispatch. Build also runs on push. Actions are SHA-pinned, permissions read-only, concurrency
cancels older same-ref runs, and available reports/APK upload even after failure. Lint remains a separate local gate.
Hosted execution/API 35 runtime is not established by the recorded local API 37 passes; verify actual CI before claiming it.
